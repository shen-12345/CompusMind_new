“校事通”开发计划

📋 技术选型与分阶段实施 📅 2026年7月 🏷️ 技术栈：FastAPI + PostgreSQL + pgvector

一、技术架构总览

1.1 最终技术栈

层级技术选型说明
前端框架Vue 3 + Element Plus上手快、单文件组件开发效率高、Vite 开箱即用
后端框架FastAPI (Python 3.11+)异步支持好，自动生成 OpenAPI 文档
关系数据库PostgreSQL 15+支持 JSONB、全文检索、窗口函数
向量数据库pgvector 扩展PostgreSQL 内置，无需额外部署
LLM 模型DeepSeek / 通义千问中文能力强，API 成本低
Embedding 模型text-embedding-v3 / bge-large中文语义检索效果好
文档解析PyMuPDF + python-docx + PaddleOCR轻量，无 GPU 依赖（OCR 可选）
文件存储本地文件系统（分层目录）前期够用，后续可迁 MinIO
密码加密bcrypt行业标准
反向代理Nginx静态文件服务 + 转发
✅ 组件数：6 个（前端 / FastAPI / PostgreSQL / Nginx / LLM API / 文件系统）
相比原方案减少了 Dify、Redis、MinIO、MinerU 四个组件，大幅降低部署和维护成本。

1.2 为什么用 pgvector 而不是单独部署向量数据库

方案优点缺点
pgvector无需额外部署，数据与业务表在一起方便事务管理，备份简单向量检索性能不如专用库（但对 10 万级 chunk 完全够用）
单独 Qdrant/Milvus检索性能更强，支持更复杂的索引多一个服务要部署维护，向量数据与业务数据分离

结论：单校园 MVP 阶段，政策文档数量有限（预估 250 个政策，约 5000-10000 个 chunk），pgvector 完全够用。

1.3 文件存储目录结构

uploads/ ├── policies/ # 辅导员上传的政策文档 │ └── {policy_id}/ │ ├── original.pdf # 源文件 │ └── parsed.md # 解析后的 Markdown 文本 │ └── materials/ # 学生上传的申请材料 └── {application_id}/ ├── {material_id}_申请表.pdf ├── {material_id}_成绩单.pdf └── ...

1.4 RAG 架构（自定义，无 Dify）

┌──────────────────────────────────────────────────┐ │ RAG Pipeline 架构 │ └──────────────────────────────────────────────────┘ 【索引阶段（文档上传时异步执行）】 文档 → PyMuPDF/python-docx 解析 → 纯文本 → 按段落/chunk_size=512 切片 → 调用 Embedding API → 向量 (1536维) → 存入 pgvector (policy_chunks 表) 【检索阶段（学生提问时实时执行）】 学生问题 → Embedding API → 查询向量 → pgvector 余弦相似度检索 (Top-K=5) → 同时元数据过滤 (学历+学院+年级) → 返回相关原文段落 【生成阶段（学生提问时实时执行）】 检索结果 + 学生问题 → LLM API → 生成回答 → 回答中标注来源（政策名称+章节）

阶段 2：文档上传与 LLM 解析（第 3-4 周）

核心设计：

解析流程（异步双轨并行）
轨道一：文档 → PyMuPDF/python-docx → 纯文本 → LLM 提取结构化字段 → 存入 policy_metadata
轨道二：文档 → 文本切片 → Embedding API → 向量 → 存入 pgvector

切片策略：按逻辑段落切分，chunk_size=512 tokens，overlap=64 tokens
提取字段：项目名称、截止时间、硬性门槛、互斥项、材料清单、评选流程、联系方式

4.3 关键设计决策

决策点方案理由
提交申请时绑定辅导员根据学生学院自动匹配辅导员每个学院导员固定，无需手动指定
辅导员角色临时替代支持代理委托机制，辅导员可指定临时替代人请假/出差时审核不中断
双学位学生以主学院为准进行政策过滤避免重复计算和混淆
毕业后账号处理账号置为失效，进行中的申请标记为"已失效"数据保留但不可操作
政策跨学年更新导员上传新版覆盖旧版，旧版自动归档不自动清理，由导员控制
数据导出支持导出为 Excel学校存档和审计需要
CAS/教务对接MVP 不做，用虚拟数据模拟后续稳定后接入
邮件通知辅助站内通知，审核结果通过邮件发送提高触达率
学生主动放弃提供"放弃申请"功能，状态变为"已放弃"避免状态卡死
纸质版提交留痕学生提交纸质版时拍照上传作为凭证避免"已提交/未收到"纠纷
修改次数限制不做限制避免过度约束
同一学生同一政策限制唯一索引 (user_id, policy_id)防止重复申请，提交前可修改
状态流转严格状态机，非法跳转被拒绝防止数据异常
批量审核不实现材料需人工逐份审核
通知超时升级仅提醒辅导员，不升级至校级避免过度干预
文件存储本地文件系统 + 分层目录MVP 够用，后续可迁
向量检索pgvector，MVP 先用，后续可换数据量小够用，迁移成本低
PDF 预览vue-pdf-embedVue 3 原生封装，开箱即用
Agent 降级LLM 不可用 → 关键词检索保证基本可用性
对话上下文压缩超 10 轮时提取关键信息压缩不丢弃，保留有效信息
敏感信息加密身份证号、家庭信息等 AES-256 加密存储数据安全合规
文件访问权限文件 URL 使用临时签名，有效期 5 分钟防止越权访问
操作日志所有关键操作记录审计日志，不可删除追溯和纠纷处理
移动端MVP 仅 PC 网页端，后续迭代迁移聚焦核心功能

五、风险评估

风险概率影响应对策略
LLM API 不稳定/延迟高中高多模型切换（DeepSeek/通义千问互备），超时降级
pgvector 检索性能不足低中chunk 数量预期 < 1 万，完全够用；如不够加 IVFFlat 索引
本地文件系统空间不足低中监控磁盘使用率，>80% 预警，可随时迁移到 MinIO
前端开发资源不足中高优先使用 Element Plus 模板，减少定制开发
用户需求在开发过程中变更高中每阶段结束有验收标准，变更进入下一阶段
PostgreSQL JSONB 字段设计不合理低低JSONB 灵活，可随时调整字段结构

本开发计划基于 2026 年 7 月技术选型讨论结果制定。
