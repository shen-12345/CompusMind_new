第1章 文档说明

1.1 文档目的

本文档为“校事通”智能政策问答平台的产品需求文档（PRD），旨在为开发团队提供完整、清晰、可执行的需求说明，作为项目开发、测试和验收的依据。

1.2 文档范围

本文档覆盖“校事通”第一版（MVP）的全部功能需求、数据模型设计、技术选型及分阶段开发计划。

第2章 产品概述

2.1 产品背景

目前学校内部的政策信息（如奖学金申请、国际会议参会报销申请等）主要通过辅导员在年级QQ群中发送通知的方式进行传达，存在以下三大核心痛点：

序号痛点描述
1信息淹没并非所有学生都需要申请每类奖学金或报销，大部分学生对无关通知选择忽略，导致真正需要申请的学生也因习惯性忽略而错过信息
2回溯困难通知通常提前一到两周发布，但学生往往在截止前一两天才开始准备，需要在QQ群中翻找历史聊天记录，耗时且容易遗漏
3版本混淆每年的申请政策文件可能有变化，学生在QQ群中搜索到的可能是已弃用的旧版文件，导致材料填写错误

2.2 产品目标

构建一个面向高校师生的智能政策问答与多级申请协同平台，核心价值：

  • 找得到：政策文档结构化归档，可检索、可追溯
  • 看得懂：清晰展示政策要点与申请进度
  • 问得清：基于RAG的智能问答，精准回答政策相关问题
  • 申得顺：全流程申请进度跟踪，辅导员初审与终核，校级管理员最终审批

2.3 用户角色

角色标识核心职责
普通学生student查询政策、智能提问、收藏政策、启动申请进度跟踪、上传电子材料、提交纸质版
学院辅导员teacher上传政策文档、预览纠错、发布政策、初审电子版材料、终核纸质版材料（核验齐全性与签章）
校级管理员admin按项目分类审批辅导员提交的纸质版材料（合规性审查）、发布全校级政策

2.4 产品边界

包含范围：政策文档归档与管理、学生端政策信息看板、智能问答Agent、申请进度跟踪（含电子材料上传）、辅导员初审与终核、校级管理员审批、政策收藏与状态管理

明确不包含（本期不做）：

功能模块不做的理由
即时性紧急通知推送QQ群已有成熟方案
移动端APP/小程序首期聚焦PC端
跨学历导员混岗管理现实中本科/研究生导员独立管理
定时发布草稿箱手动发布可替代
原子规则库与自动资格预判规则模板易膨胀且主观性强
电子签章/电子签名纸质材料仍需线下提交

第3章 功能需求详细描述

3.1 用户认证模块

3.1.1 功能描述

系统提供基于账号密码的登录与身份识别功能。

3.1.2 功能细节

功能点描述
用户登录用户输入用户名和密码进行登录
身份识别登录后系统识别用户角色（学生/辅导员/管理员），加载对应权限视图
密码修改首次登录强制修改初始密码
会话管理登录后保持会话状态，超时自动退出

3.1.3 边界条件

场景处理方式
用户名不存在提示“用户名或密码错误”
密码错误超过5次锁定账号15分钟
未登录访问需授权页面重定向至登录页
会话超时（30分钟无操作）自动退出，提示重新登录

3.1.4 异常处理

异常处理方式
数据库连接失败提示“系统繁忙，请稍后重试”
密码加密失败记录日志，提示“注册失败，请联系管理员”

3.2 辅导员端 — 文档上传与自动解析

3.2.1 功能描述

辅导员上传政策通知文档，系统自动完成结构化字段提取和全文向量化入库。

3.2.2 功能细节

上传要求：

项目说明
支持格式PDF、Word（.docx）、扫描件PDF（自动OCR识别）
必填标签适用年级（如“2023级、2024级”）
文件大小限制≤ 20MB

系统自动解析（双轨并行）：

轨道一：结构化字段提取

调用LLM从文档中提取以下关键字段，存入元数据表：

字段说明是否必填示例
项目名称政策/项目的正式名称是“2026年校长奖学金”
截止时间材料提交截止日期时间是“2026-09-20 17:00”
硬性门槛申请必须具备的条件否“需获得过校级一等奖学金”
互斥项不可同时申请的其他项目否“不可与国家奖学金兼得”
材料清单申请所需提交的全部材料列表是[“申请表”, “成绩单”, “导师推荐信”]
📌 材料清单获取方式：系统由LLM自动从通知文件中提取，导员在解析预览页核对并修正，无需手动填写。

轨道二：全文向量化入库

将文档全文进行文本提取、切片，调用Embedding模型生成向量，存入向量知识库。

结构化信息提取的技术流程：

步骤说明工具/方法
1. 文档解析将PDF/Word转换为纯文本或MarkdownMinerU / Unstructured
2. 内容分块按逻辑段落切分LangChain文本分割器 / Dify内置分块
3. 相关性分类判断段落是否包含目标信息LLM（DeepSeek/通义千问）
4. 结构化提取按预设JSON Schema提取关键字段LLM + Dify参数提取器节点

3.2.3 边界条件

场景处理方式
上传文件为空或损坏提示“文件无效，请重新上传”
文件格式不支持提示“仅支持PDF和Word格式”
文件超过20MB提示“文件过大，请压缩后上传”
LLM提取字段为空该字段标记为“⚠️ 未识别，请手动填写”
LLM提取置信度 < 80%该字段橙色高亮，提示导员重点核对

3.2.4 异常处理

异常处理方式
LLM服务不可用提示“解析服务暂时不可用，请稍后重试”，保留草稿
向量化服务不可用禁止发布。提示“文档解析完成，但向量化服务暂时不可用，请稍后重试或联系管理员”，保留草稿状态，等待恢复后自动重试
向量化入库失败整体事务回滚。元数据和向量数据均不入库，提示“系统处理失败，请稍后重试”
OCR识别失败提示“文档文字识别失败，请上传文字版PDF或手动输入关键信息”

3.3 辅导员端 — 解析预览与发布管理

3.3.1 功能描述

导员核对系统提取的结构化信息，确认无误后发布政策。

3.3.2 功能细节

解析预览页展示内容：

  • 所有提取的结构化字段（项目名称、截止时间、硬性门槛、互斥项、材料清单）
  • 低置信度字段（< 80%）以橙色边框高亮
  • 空值字段显示“⚠️ 未识别，请手动填写”
  • 文档全文预览（供核对上下文）

导员可执行操作：

  • 点击任意字段进行在线编辑修改
  • 增加或删除材料清单中的项目
  • 点击“确认发布”：政策正式生效，学生端可见
  • 点击“保存草稿”：政策保持草稿态，学生端不可见

发布前置条件：导员点击“确认发布”后，系统执行以下原子化操作：

  1. 写入元数据到MySQL
  2. 写入向量数据到向量知识库
  3. 更新政策状态为“已发布”
⚠️ 以上三步必须全部成功，否则整体事务回滚，政策保持草稿态。

三态流转：

状态含义学生端可见性
草稿态文档已上传，解析完成，尚未发布❌ 不可见
待确认导员正在预览页核对信息❌ 不可见
已发布导员已确认发布，政策正式生效✅ 可见

3.3.3 边界条件

场景处理方式
必填字段（项目名称、截止时间、材料清单）为空禁止发布，提示“请完善必填信息”
截止时间早于当前时间警告“截止时间已过期，请确认”
同一项目已存在生效政策警告“该项目已有生效政策，发布后将自动归档旧版”

3.4 辅导员端 — 电子版初审

3.4.1 功能描述

辅导员在线初审学生提交的电子版材料，按项目分类查看和处理。

3.4.2 功能细节

项目分类视图（第一级）：

📋 待初审项目分类
├── 国家奖学金（12 份待审）
├── 校长奖学金（5 份待审）
├── 国际会议报销（3 份待审）
└── 助学金申请（8 份待审）

学生申请列表（第二级）：

辅导员点击具体项目后，进入该项目下的学生申请列表：

展示字段说明
学生姓名申请者姓名
学号申请者学号
提交时间电子版材料提交时间
操作点击进入审核详情页

审核详情页功能：

  • 在线预览学生上传的电子版材料（PDF/JPG/PNG）
  • 下载材料到本地
  • 初审通过：点击后状态变为“初审通过”，学生端收到通知
  • 需修正：填写修正意见（可针对单个材料反馈），状态变为“需修正”，学生端收到修正通知
🔒 权限控制：辅导员只能看到自己所辖学院学生的申请。不同学院的数据相互隔离。

3.4.3 边界条件

场景处理方式
待初审列表为空显示“暂无待初审申请”
学生未上传任何材料不进入待初审列表
导员未填写修正意见直接退回强制要求填写意见

3.5 辅导员端 — 纸质版终核

3.5.1 功能描述

辅导员终核学生提交的纸质版材料，重点检查材料齐全性与签章合规性。

3.5.2 功能细节

辅导员在“待终核列表”中点击学生申请，进入终核详情页。页面展示该生已提交的电子版材料清单，供导员逐项核对纸质版：

核验项目说明
材料是否齐全对照清单，确认学生是否提交了所有要求的纸质材料
签章是否完备重点检查每份材料上要求的签名、公章、日期等是否完整、合规（如：是否为单位公章而非部门章、签名是否为本人手签等）
信息是否一致核对纸质版内容与电子版是否一致（此项为辅助检查，非唯一重点）

所有项目核验无误后，点击“终核通过”，状态变为“已交校级待审批”，系统将该申请推送至校级管理员端。

如发现问题，可选择“退回修正”并注明具体原因（如：“缺少学院公章”或“推荐信未签名”）。

3.5.3 边界条件

场景处理方式
纸质版缺少盖章退回修正，注明“缺少XX单位公章”
纸质版缺少签名退回修正，注明“缺少XX人签名”
材料不齐全退回修正，注明“缺少XX材料”

3.6 校级管理员 — 最终审批

3.6.1 功能描述

校级管理员（学生处、国际交流处、财务处等）对辅导员终核通过并提交上来的纸质版材料进行最终合规性审批。

📌 审批对象：校级管理员审批的是纸质版材料，而非电子版。辅导员终核通过后需将纸质材料整理上交至校级部门，由校级管理员进行最终审批。

3.6.2 功能细节

前置条件：该申请已通过辅导员终核（纸质版材料已由辅导员核验齐全并签章确认）。

第一级：按项目分类

📋 待审批项目列表
├── 国家奖学金（12 份待审）
├── 校长奖学金（5 份待审）
├── 国际会议报销（3 份待审）
└── 助学金申请（8 份待审）

第二级：项目下按学院分组

点击具体项目后，展开该项目的待审批列表，按学院分组展示：

📋 国家奖学金（12 份待审）
├── 计算机学院（4 份）
│   ├── 张三（20240301）
│   ├── 李四（20240305）
│   └── ...
├── 人文学院（3 份）
│   ├── 王五（20240112）
│   └── ...
└── 经济管理学院（5 份）
     ├── 赵六（20240208）
     └── ...

设计说明：

  • 每个学院分组显示待审批份数，管理员可快速了解各学院的提交进度
  • 点击具体学生行，进入审批详情页，预览纸质版材料的电子扫描件（如有）或查看辅导员终核记录
  • 支持按项目筛选、按学院分组浏览，便于集中处理同一学院的多份申请

审批操作：

  • 审批通过：确认纸质版材料符合政策要求后，点击通过，流程正式结束
  • 审批驳回：如发现材料不符合政策规定（如成绩未达标、论文不在目录内），填写驳回理由，退回至学生端，状态变为“需修正”

3.6.3 权限隔离

校级管理员角色可查看的项目
学生处管理员国家奖学金、校长奖学金、助学金等学生奖励类
国际交流处管理员国际会议报销、出国交流资助等
财务处管理员各类报销申请

3.6.4 边界条件

场景处理方式
待审批列表为空显示“暂无待审批申请”
审批驳回未填写理由强制要求填写驳回理由
同一项目下某学院无申请该学院分组不显示

3.7 辅导员端 — 数据统计看板

3.7.1 功能描述

展示每个政策的统计数据，帮助导员掌握申请进度。

3.7.2 功能细节

统计指标含义
查看人数点击查看该政策详情的学生数
准备申请人数点击“开始准备”的学生数
已提交电子版人数已完成电子版提交的学生数
待初审人数电子版已提交、等待导员初审的学生数
待终核人数初审通过、已提交纸质版、等待终核的学生数
已交校级待审批人数终核通过、已上交校级部门的申请数
已完成人数校级审批通过、流程完结的学生数

3.8 学生端 — 综合信息看板

3.8.1 功能描述

学生登录后默认进入信息看板，展示可申请的政策卡片列表。

3.8.2 功能细节

  • 展示当前可申请的政策卡片列表
  • 每张卡片包含：政策名称、截止日期倒计时、发布学院、当前申请进度状态
  • 列表自动过滤：仅显示符合该生学历 + 学院 + 年级的有效政策
  • 按截止时间由近及远排序

3.8.3 边界条件

场景处理方式
无可申请政策显示“暂无符合条件的政策”
政策已过期不显示在看板中

3.9 学生端 — 智能问答Agent

3.9.1 功能描述

基于RAG的智能问答助手，回答政策相关问题。

3.9.2 功能细节

  • 入口：看板页面右下角的悬浮对话框
  • 支持多轮对话与上下文记忆
  • 回答能力覆盖：政策内容查询、申请条件咨询、材料清单询问、截止时间查询等
  • 所有事实性回答必须标注来源（政策名称及章节）
  • 当学生询问“需要什么材料”或“怎么申请”时，Agent回答后主动追加引导：“是否需要将此申请添加到您的个人进度跟踪中？[是的，开始准备]”

工具调用接口：

工具名称功能描述输入参数输出
截止时间查询器查询特定项目的材料提交截止时间项目名称/政策ID截止时间
材料清单检索器查询特定项目所需提交的材料清单项目名称/政策ID材料列表
政策原文摘录器语义检索返回相关原文段落用户问题最相关的3段原文+来源

调用策略：三个工具无依赖关系，允许并行调用。

3.9.3 边界条件

场景处理方式
问题与政策无关回复“未找到相关信息，建议联系辅导员确认”
多轮对话超过10轮提示“如需继续咨询，请重新提问”
工具调用超过5步强制转人工提示
工具调用超过3秒无返回触发兜底话术

3.10 学生端 — 申请进度跟踪器

3.10.1 功能描述

学生启动申请后，系统提供全流程进度跟踪面板。

3.10.2 功能细节

启动与材料清单：

  • 学生点击“开始准备”，系统生成申请进度跟踪面板
  • 面板展示材料清单（来源于导员发布时确认的版本）
  • 每项材料对应一个独立的上传入口
  • 逐项上传电子版文件（PDF/JPG/PNG，≤5MB）
  • 系统实时记录每项材料的“已上传/未上传”状态

第5章 技术选型及理由

5.1 技术选型总览

层级技术选型选型理由
前端框架React + Ant Design组件丰富、生态成熟、适合PC端管理后台快速开发
后端框架Python Flask / FastAPI轻量、灵活、与AI生态（LangChain等）集成友好
数据库MySQL 8.0成熟稳定、事务支持完善、适合结构化数据存储
向量数据库Dify内置向量库（Qdrant）与Dify平台深度集成，开箱即用
文档解析MinerU / Unstructured开源、支持OCR、对中文文档支持良好
LLM框架Dify低代码Agent编排、内置RAG能力、可视化工作流
LLM模型DeepSeek / 通义千问中文能力强、API成本低、支持Function Calling
Embedding模型text-embedding-v3 / bge-large中文语义检索效果好
对象存储本地文件系统 / MinIO存储学生上传的电子材料
密码加密bcrypt行业标准、抗彩虹表攻击

5.2 核心组件选型详解

5.2.1 文档解析：MinerU + Dify参数提取器

解析流程：

  1. 文档解析：使用MinerU将PDF/Word转换为Markdown或JSON
  2. 内容分块：将长文本按逻辑段落切分
  3. 相关性分类：LLM判断段落是否包含目标信息
  4. 结构化提取：使用Dify的参数提取器节点，按预设JSON Schema提取字段

选型理由：

  • MinerU对中文PDF支持良好，支持OCR和复杂版式
  • Dify参数提取器可视化配置，无需编写复杂代码
  • 组合方案兼顾解析质量与开发效率

5.2.2 LLM应用开发平台：Dify

选型理由：

  • 开源、支持私有化部署
  • 内置RAG模块，支持混合检索（关键词+向量+元数据过滤）
  • 可视化Agent编排，支持工具调用
  • 低代码特性降低开发门槛

5.2.3 检索策略：RAG混合检索

检索执行顺序：

  1. 元数据过滤（SQL查询）：根据学生学历+学院筛选候选文档
  2. 混合检索：在候选集内并行执行BM25关键词检索 + 向量检索
  3. RRF融合：合并排序，返回Top K结果
